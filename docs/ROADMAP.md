## Этап 3. Авторизация

Контракт — `docs/auth_api.md`, stage — `https://mentorix-api-stage.onrender.com`.

### Что сделано

**Сеть и хранилище (`lib/core/`)**
- `network/dio_factory.dart` — два `Dio`: `plain` (вход, logout, refresh, повтор) и `api`
  с `AuthInterceptor`. `contentType: application/json` задан явно, таймауты 60 секунд.
- `network/auth_interceptor.dart` — `QueuedInterceptor`: Bearer, упреждающий refresh
  за 60 секунд до `expires_at`, на 401 один общий refresh, повтор один раз через `plain`,
  при 401 на refresh — очистка токенов и событие в `SessionExpiredNotifier`.
- `storage/token_storage.dart` — `flutter_secure_storage`: `access_token`, `refresh_token`,
  `expires_at`, `user_id`; флаг установки и обработка сбоя Keystore по разделу 5 `CLAUDE.md`.
- `config/api_config.dart` (`--dart-define=API_BASE_URL`), `config/social_auth_config.dart`
  (плейсхолдеры client id), `logging/app_logger.dart`, `widgets/app_snack_bar.dart`.
- `router/` — `RouteNames`, `OnboardingFlow`, редирект по сессии.

**Фича `lib/features/auth/`**
- `domain` — `UserProfile`, `InviteAcceptance`, `SocialCredential`, sealed `AuthFailure`,
  `AuthRepository`, `SocialAuthProvider`.
- `data` — `AuthRemoteDataSource` (все эндпоинты из документа), модели с `fromJson`,
  `AuthErrorMapper` (по `code`), `GoogleAuthProvider`, `AppleAuthProvider`,
  `PendingAppleNameStorage`, `AuthRepositoryImpl`.
- `presentation` — `SessionCubit`, `LoginCubit`, `TelegramLinkCubit`, `InviteCubit`;
  экраны: заставка, вход, предложение Telegram, ввод кода, приглашение; `HomeScreen` —
  заглушка с именем и кнопкой выхода.

### Решения

| Вопрос | Решение |
|---|---|
| Ошибки | sealed `AuthFailure`, перевод только в `presentation`. `enum AppErrorCode` не используется; правило в `CLAUDE.md` обновлено под это решение |
| Ошибки API | `{"code","message"}`: ветвление только по `code` (`ApiErrorCodes`), `message` не разбирается и не показывается; неизвестный `code` — общий текст по статусу. `InviteConflictParser` удалён (2026-10-13) |
| 429 | ничего не повторяется, показывается сообщение |
| Параллельные 401 | очередь `QueuedInterceptor` + сравнение токена запроса с текущим: запрос, чей 401 пришёл после чужого refresh, просто повторяется с новым токеном |
| Упреждающий refresh | порог 60 секунд до `expires_at` (константа в `AuthInterceptor`) |
| Публичные эндпоинты | `/auth/google`, `/auth/apple`, `/auth/logout` идут через основной `Dio` с `extra: {skipAuth: true}`: перехватчик не подставляет Bearer, не делает refresh и не трогает 401 (на входе это «токен провайдера не принят», а refresh перед logout испортил бы refresh-токен в теле). По путям перехватчик не определяет. `plainDio` остался только для refresh и повтора запросов |
| Упреждающий refresh упал не по 401 | сеть, 5xx, 429: запрос уходит с текущим токеном (он ещё действует), 401 разберёт `onError`. После неудачи 30 секунд следующие запросы не пробуют обновлять токен: иначе очередь ждала бы таймаут refresh на каждом запросе |
| Формат `expires_at` | строка ISO 8601 в UTC (ответ бэкенда 2026-10-13); всё остальное — `null` (тогда обновление только по 401) |
| `user_id`, `trainer_id` | UUID строкой; число или `null` — `FormatException` → `UnknownFailure` |
| Нет сети при старте | `SessionUnknown(failure)` + «Повторить», токены не стираются и на вход не выбрасывают |
| `SessionCubit` | единственный экземпляр (`registerLazySingleton`) — исключение из «кубиты — factory»: на сессию смотрят роутер и экраны |
| Порядок экранов | `/auth/me` → `/client/trainers` → если `telegram_linked == false` и предложение не закрыто, Telegram → приглашение (только если `items` пуст и шаг не закрыт) → главный. Пройденные шаги хранятся в `shared_preferences` по `user_id` |
| Главный экран | недоступен, пока не закрыт шаг приглашения (его можно отложить кнопкой «Позже») |
| Telegram → профиль | после `telegram/link` оба токена и `user_id` заменяются, кеш профиля сброшен, `/auth/me` запрашивается заново; если `/auth/me` упал, повтор не шлёт использованный код |
| Apple | iOS/macOS — нативно, Android — веб-поток (`APPLE_SERVICE_ID`, `APPLE_REDIRECT_URI`, активити `SignInWithAppleCallback`); перед входом случайный `state`, сверка с `credential.state` до отправки токена. Имя хранится в secure storage, пока профиль не подтвердит, что имя на сервере есть (или `PATCH /auth/me` его не запишет) |
| Имя из Apple | после `/auth/me` с пустым именем и известным именем Apple — `PATCH /auth/me` (не больше 100 символов) и повторный `/auth/me`; существующее имя не трогается; сбой PATCH только в debug-лог (`name fallback: PATCH sent / skipped (server has name) / failed`), вход не ломается, имя остаётся в `PendingAppleNameStorage`. Один раз за вход |
| `PATCH /auth/me` | в контракте нет описания ответа: после запроса профиль загружается заново |
| Подписка | поле `subscription` не разбирается: структура для не-клиентов в контракте не описана |
| Логи | Talker (`talker_flutter`, `talker_dio_logger`): `AppLogger` и `DebugLog` пишут в один `Talker`, запросы — `MaskedTalkerDioLogger` на обоих `Dio` (метод, путь, статус, время, заголовки, тела). Секреты маскируются `SecretMasker` (`***`). Только debug; экран логов — долгое нажатие на заголовок профиля (см. «Логи на Talker») |

### Сценарии проверки

Без client id (плейсхолдеры в конфиге):
1. Холодный старт без сессии: заставка → экран входа.
2. «Продолжить с Google»: сообщение «способ входа недоступен», приложение не падает.
3. На iOS видна кнопка Apple, на Android — только Google.
4. Переключатель темы и язык работают на экране входа так же, как на главном.

С настоящими client id и stage-бэкендом:
5. Вход через Google → профиль → (если Telegram не привязан) предложение Telegram →
   «Нет, пропустить» → приглашение → «Позже» → главный экран с именем или почтой.
6. Перезапуск приложения: сразу главный экран, без повторного входа и шагов онбординга.
7. «Выйти» → экран входа; перезапуск → экран входа.
8. Telegram: код от бота → `Продолжить` → переход к приглашению; повторный вход под
   привязанной записью не предлагает Telegram снова.
9. Приглашение: ссылка целиком, `inv_…` и голый токен — все три принимаются; ошибки
   (несуществующее, просроченное, чужое) показывают понятные сообщения на ru и en.
10. Stage «спит»: первый запрос после простоя ждёт до минуты и не падает по таймауту.
11. Самолётный режим на старте с сохранённой сессией: сообщение и «Повторить», выхода
    на вход нет.

Автоматически покрыто (71 тест): три параллельных 401 → один refresh и три повтора
с новым токеном; refresh вернул 401 → токены очищены, сессия завершена один раз;
повтор не зацикливается; 429 и сбой сети не стирают сессию; упреждающий refresh;
порядок экранов; кеш профиля и токены после привязки Telegram; имя Apple.

### Профиль и удаление аккаунта (2026-10-13)

Контракт — `docs/backend_answers.md`, пункт 3; поведение — `docs/APP_LOGIC.md`.

**Сделано**
- Экран профиля `/profile` (`ProfileScreen`): имя, почта, «Выйти», «Удалить аккаунт».
  С главного экрана — кнопка «Профиль»; выход с главного перенесён в профиль.
- Диалог подтверждения: что удалится и что восстановить нельзя.
- `DELETE /auth/me`: сначала без тела; 422 `apple_authorization_required` →
  окно Apple → повтор с `apple_id_token` и `apple_authorization_code`, на Android ещё
  `apple_redirect_uri`, `Content-Type: application/json`. Код берётся после 422.
- Ответы: 204 и 404 `user_not_found` — токены стёрты, `GoogleSignIn.disconnect()`,
  экран входа; 401/400 Apple и 403 — «Повторить» (окно Apple снова); 409 — в
  поддержку; 502/503 — позже.
- `AuthInterceptor`: 401 `invalid_id_token` не запускает refresh и не повторяется
  (иначе потратился бы одноразовый код Apple).

**Решения**
- Ошибки удаления разбираются эндпоинт-специфичным маппером
  (`AuthErrorMapper.accountDeletion`, он приоритетнее общего разбора по `code`):
  `invalid_id_token` на входе значит «токен не принят», на удалении — «повторите окно».
- После отказа Apple повтор сразу показывает окно Apple. После 502/503 — нет: у
  аккаунта без входа через Apple окно не нужно вовсе, ответит и так 422.
- `SocialAuthProvider.disconnect()` не бросает: аккаунт уже удалён, сбой Google
  только в лог.

**Проверить на устройстве**
- Google-аккаунт: удалить → вход тем же Google создаёт новый пустой аккаунт.
- Apple-аккаунт на iOS и Android: окно Apple → удалено; приложение исчезает из
  «Вход с Apple» в настройках Apple ID.
- Пока на stage нет ключа Apple, такие аккаунты получат 503 `provider_not_configured`
  («Не удалось удалить, попробуйте позже») — это ожидаемо, бэкенд обещал убрать.
- Аккаунт тренера или администратора (409) — сообщение «обратитесь в поддержку».

### Debug-диагностика (2026-10-13)

Для проверки на устройстве. Всё — только в debug-сборке, в release ничего нет.

**Сделано**
- Вывод переведён с `dart:developer` на `debugPrint` через `DebugLog`
  (`lib/core/logging/debug_log.dart`): строки видны в консоли `flutter run` и в Debug
  Console VS Code. Формат — `[mentorix.http] <время UTC> <метод> <путь> <статус>
  code=<code>`. Теги: `mentorix.http`, `mentorix.apple`, `mentorix.delete`, `mentorix`
  (предупреждения и ошибки). В release `AppLogger` пишет через `dart:developer`, как
  раньше.
- Статус и `code` рядом с текстом ошибки на экране: «Не удалось удалить аккаунт.
  Попробуйте позже. (503 provider_not_configured)»; без ответа сервера — тип сбоя
  (`connectionError`). Берётся из `ApiErrorDetails` у `AuthFailure`, которое
  маппер заполняет только в debug.
- Вход через Apple: что вернул Apple (`givenName`/`familyName` — значения, есть ли
  токен и код — да/нет, совпал ли `state`); есть ли `name` в теле `POST /auth/apple` и
  его значение; откуда имя — из ответа Apple, из `PendingAppleNameStorage` или его нет.
- Удаление аккаунта: шаг потока (1 запрос без тела → 2 получен 422 → 3 окно Apple
  открыто/вернулось/закрыто → 4 повтор с телом → done) и есть ли в теле
  `apple_id_token`, `apple_authorization_code`, `apple_redirect_uri` (только да/нет).

**Решения**
- Значения токенов и authorization_code не пишутся нигде, даже в debug.
- Имя из Apple — персональные данные, пишется только в debug и только по просьбе
  (отладка того, отдаёт ли Apple имя).
- `kDebugMode` — константа, в тестах всегда `true`, поэтому release в тестах
  имитируется `DebugLog.debugModeOverride = false`.
- `AppLogger.dioError` в debug молчит: ту же строку пишет интерцептор.

### Логи на Talker (2026-10-13)

Заменяет `debugPrint`-вывод из «Debug-диагностики» (её содержание — какие данные
пишутся — сохранилось).

**Сделано**
- Пакеты `talker_flutter`, `talker_dio_logger`. Единственный `Talker` —
  `AppTalker`; `AppLogger` (интерфейс прежний) и `DebugLog` пишут в него. Теги
  `[mentorix.apple]`, `[mentorix.delete]` остались в тексте.
- `ApiLogInterceptor` удалён: на обоих `Dio` — `MaskedTalkerDioLogger`
  (метод, путь, статус, время ответа, заголовки, тела запроса и ответа).
- Маскировка (`SecretMasker`, `***`): `Authorization` (а также `Cookie`,
  `Set-Cookie`); в телах и вложенных JSON — `access_token`, `refresh_token`,
  `id_token`, `apple_id_token`, `apple_authorization_code`; `code` — только в теле
  запроса `/auth/telegram/link`.
- Экран логов `TalkerScreen`: долгое нажатие на заголовок профиля
  (`DebugLogsEntry`).
- Только debug: в release нет `Talker`, логгера в цепочке `Dio` и жеста на
  заголовке; `AppLogger` и `DebugLog` ничего не делают. Тесты через
  `DebugLog.debugModeOverride = false`.

**Решения**
- Логгер пишет **копию** с замаскированными значениями: запись Talker хранит
  ссылки и формирует текст позже, а `AuthInterceptor` меняет те же заголовки.
  Настоящие запрос и ответ едут дальше без изменений.
- `MaskedTalkerDioLogger` стоит в основном `Dio` **после** `AuthInterceptor`:
  иначе в записи не было бы заголовка `Authorization`. Цена: 401, который
  перехватчик обновил и повторил, в журнале основного `Dio` не виден — виден
  refresh и повтор (их пишет журнал `plainDio`, а причину — строка
  `AuthInterceptor`, см. ниже).
- Дополнительно к списку из задачи маскируется поле `token` (одноразовый токен
  приглашения тренера в `/client/invites/accept`) — это такой же секрет.
- `code` в ответах не маскируется: это код ошибки, он нужен для отладки.
- В release теперь нет и `developer.log`: раньше `AppLogger` писал туда ошибки.
- Пробел в журнале основного `Dio` закрыт строкой из `AuthInterceptor`
  (`AppLogger.http`, только debug): «401 на GET /auth/me → refresh» или
  «401 на GET /x → повтор с уже обновлённым токеном». Второй логгер не ставился;
  значения токенов в строку не попадают. 401 `invalid_id_token` и публичные
  запросы строки не дают: перехватчик их не обрабатывает.
